# ocr_eval — 한국어 OCR 평가 프레임워크

한국어 다국어 혼합 문서 OCR 인식 품질 평가 도구. **지표 하나로 판단하지 않는 것**이 설계 원칙입니다.

모델·프레임워크에 의존하지 않습니다. 입력은 정답 문자열과 예측 문자열뿐이고, 표준 라이브러리만 씁니다.

```bash
python -m ocr_eval.evaluate --gt gt --pred pred --mode line
```

---

## 왜 지표가 5개인가

한국어 다국어 혼합 문서 OCR에는 공개 표준 벤치마크가 없어서 평가셋과 평가 기준을 직접 만들어야 했습니다. 그 과정에서 **지표들이 서로 반대 신호를 보내는 상황**을 여러 번 만났고, 그때마다 원인을 찾아 지표를 추가했습니다.

### 사건 1 — Char Acc 47% vs F1 97%

학술논문 평가셋에서 문자 정확도는 46.97%인데 F1은 97.13%가 나왔습니다. 어느 쪽을 믿고 모델을 골라야 할지 알 수 없었습니다.

원인은 **2단 레이아웃의 읽기 순서**였습니다. 검출 단계가 좌·우 단을 한 줄로 합치면, 글자는 전부 맞아도 페이지 전체를 이어붙여 계산하는 편집거리가 폭발합니다.

```
GT  라인 1 : 서는 스트레스원에 대한 문제 해결적인 적극적
GT  라인 2 : 후로 쉽게 해결할 수 있는 문제에 대해서도 해결
예측 라인 1 : 서는 스트레스원에 대한 문제 해결적인 적극적 후로 쉽게 해결할 수 있는 …
              └─ 좌·우 단이 한 줄로 합쳐짐. 글자는 다 맞음
```

**결론** — 페이지 단위 평가에서는 순서에 둔감한 **F1**을, 라인 단위 평가에서는 **Char Acc**를 주 지표로 씁니다. 이 저장소가 `--mode page` 와 `--mode line` 을 나눠 둔 이유입니다. 둘은 같은 것을 다르게 재는 게 아니라 **다른 것을 잽니다.**

### 사건 2 — 잔존 오류의 대부분이 모델 잘못이 아니었다

최종 모델의 잔존 오류 14.11%를 유형별로 분해했더니 이랬습니다.

| 유형 | 비율 | 정체 |
|---|---:|---|
| `spacing_only` | **11.08%** | **정답 라벨의 공백 비일관성** |
| `substitution` | 1.52% | `–`↔`-`, `Ⅵ`↔`VI` 같은 유사 문자 |
| `missing` | 1.18% | 짧은 크롭 일부 누락 |
| `overgen` | 0.34% | 모델 과생성 |

오류의 78%가 라벨 쪽 문제였습니다. `대도시` 를 라벨이 `대 도 시` 로 띄워 놓은 경우입니다.

**결론** — `char_acc_nospace`(공백 제거 문자 정확도)를 보조 지표로 추가했습니다. 같은 모델이 76.30% → **96.97%** 로 달라 보입니다. 어느 쪽도 거짓이 아니고, **무엇을 재는지가 다를 뿐**입니다.

### 사건 3 — 일본어·중국어에서 F1이 흔들린다

일본어·중국어는 공백으로 단어를 나누지 않습니다. 공백 기준 토큰 분할에 의존하는 F1은 이 언어에서 구조적으로 불안정합니다. 실제로 최종 모델이 일중 혼재 도메인에서 Char Acc는 89.63 → 89.96으로 올랐는데 F1은 44.47 → 43.99로 내려갔습니다.

**결론** — 언어권에 따라 주 지표를 다르게 읽습니다. 지표 표에 각주를 남기지 않으면 나중에 자신도 속습니다.

## 지표

| 키 | 지표 | 정의 | 강한 점 / 약한 점 |
|---|---|---|---|
| `char_acc` | Character Accuracy | `1 − 편집거리/GT길이` | 표준. 읽기 순서 섞임에 매우 취약 |
| `char_acc_nospace` | 공백 제거 Char Acc | 공백 제거 후 동일 계산 | 라벨 공백이 불안정할 때 실질 인식력 |
| `f1` | Token F1 | 단어 multiset 기반 | 순서에 둔감. 공백 없는 언어에서 불안정 |
| `exact_acc` | Line/Page Exact | 완전 일치 비율 | 가장 엄격. 체감 품질에 가까움 |
| `ned` | Normalized Edit Distance | 유사도 비율 평균 | 관대. 개선 추세 확인용 |
| `cer` / `wer` | 오류율 | `1 − 정확도` | 논문 표기용 |

`char_acc` 는 **음수가 나올 수 있습니다.** 예측이 정답과 완전히 다르면 편집거리가 정답 길이를 넘습니다. 버그가 아니라 "인식 실패"의 극단 표시입니다. 실제로 중국어 사전탑재 모델을 한국어 문서에 돌렸을 때 −811%가 나왔습니다.

## 사용법

### 디렉토리 비교

```
gt/{domain}/{page}.txt        pred/{domain}/{page}.txt
```

```bash
# 라인 단위 (같은 줄 번호끼리 비교) — 오류 유형 분류 포함
python -m ocr_eval.evaluate --gt gt --pred pred --mode line

# 페이지 단위 (페이지 전체를 이어붙여 비교)
python -m ocr_eval.evaluate --gt gt --pred pred --mode page

# 특정 도메인만, 결과 저장
python -m ocr_eval.evaluate --gt gt --pred pred \
    --domains C1_scan_old C2_hanja_mixed \
    --out-json out/result.json --out-md out/report.md
```

도메인 폴더가 없는 평평한 구조도 그대로 동작합니다.

### TSV 비교

```bash
python -m ocr_eval.evaluate --tsv pairs.tsv     # id<TAB>gt<TAB>pred
```

### 라이브러리로

```python
from ocr_eval import Accumulator, classify_error

acc = Accumulator()
for gt, pred in pairs:
    acc.add(gt, pred, classify=True)

m = acc.result()
print(m["char_acc"], m["char_acc_nospace"], m["f1"])
print(m["error_types"])          # spacing_only / substitution / missing / overgen

classify_error("대도시 인구", "대 도시 인구")     # 'spacing_only'
classify_error("<표1−45>", "<표1-45>")          # 'substitution'
```

### 학습 데이터 편향 확인

합성 데이터에 특정 기호가 과다하면 모델이 실문서에도 그 기호를 찍습니다. 정답과 예측의 기호 출현 빈도를 비교하면 바로 드러납니다.

```python
from ocr_eval import bias_symbol_counts
bias_symbol_counts(gt_text, pred_text)   # {'△': {'gt': 0, 'pred': 137}, ...}
```

## 평가 결과를 읽을 때

1. **집계값만 보지 마세요.** 전체 정확도 90.58%였던 모델을 텍스트 길이 구간별로 분해했더니, 30자 이하는 97~99%인데 41자 이상은 93~96%가 실패하고 있었습니다. 평균이 구간별 전멸을 덮고 있었습니다.
2. **지표가 엇갈리면 그게 신호입니다.** 어느 쪽을 고를지 고민하기 전에, 왜 엇갈리는지 먼저 봐야 합니다. 대개 평가 방식이 측정하려던 것과 어긋나 있습니다.
3. **오류를 유형별로 나눠 보세요.** 모델을 고칠 문제인지 라벨을 고칠 문제인지가 거기서 갈립니다.
